# 簡化流程規格 v0.4（草稿，待確認）

> 狀態：只有規格，尚未改程式。標 ❓ 的項目需要實測，標 🟡 的項目待營運者決定。
> 取代對象：`docs/QUEST-JOURNEY.md` 的 27 關建置流程。

## 1. 目標

| 原則 | 做法 |
| --- | --- |
| 三段流程 | ① 定位（2 題）→ ② 建置（固定範本）→ ③ 在自己的 OA 跟秘書對話修改 |
| 建置不用 AI | 部署固定範本，不產生程式碼，不扣點，每次結果相同 |
| 設計即設定資料 | 選單、卡片、回覆、秘書功能都存成客戶資料庫裡的一份設定，改了立即生效 |
| 平台不長期連著客戶 | 建置完成後，平台不保留客戶的 GitHub／Supabase／LINE 存取權 |
| 修改走 API、扣點數 | 客戶的 OA 呼叫平台 API，費用從該客戶的點數錢包扣 |
| 金鑰不經過平台 | 瀏覽器先加密，平台只轉寫密文到客戶 repo 的 Secrets |

## 2. 建置後，平台與客戶之間還剩什麼

| 項目 | 存在哪 | 說明 |
| --- | --- | --- |
| API 金鑰（`aprico_…`） | 明文只在客戶的 Supabase secrets；平台只存雜湊 | 現有 `line_oa_kit_runtime_keys`，可撤銷 |
| 點數錢包、用量紀錄 | 平台 | 現有 `line_oa_kit_points_wallets`、`line_oa_kit_ai_usage` |
| 客戶的設定資料、對話、會員資料 | 客戶自己的 Supabase | 平台不保存 |
| GitHub App 授權 | 建置完成後**由平台自動移除安裝** | 之後更新範本時，客戶重新安裝一次，完成後再自動移除 |

建置頁要用白話說清楚這一點：「建好之後，Aprico 不會連著你的帳號。你在自己的 OA 請秘書幫忙時，才會把那一句話和目前的設定送到 Aprico 處理，並扣你的點數。」

## 3. 階段一：定位（2 題）

| # | 問題 | 選項 | 對應現有資料 |
| --- | --- | --- | --- |
| 1 | 這個帳號要做什麼？ | 官方帳號選單／個人秘書／兩者都要 | `secretary.direction`：`oa`／`records`／`both` |
| 2 | 用一句話說你的目標 | 自由輸入，上限 200 字 | 現有 `goal`，交給 AI 預填（`build-prefill.ts`） |

- 依第 1 題給預設範本：選單用 `menuPresets`，秘書用 `recordPresets`（行程、收支、待辦、生活紀錄）。
- 原本 6 題需求（服務對象、目的、情境、成功條件、失敗處理、轉人工）不再問。失敗處理與轉人工給預設文字，之後在對話裡改。
- 這一段不扣點。❓ 第 2 題的 AI 預填目前是否計費，改之前要再確認。

## 4. 階段二：建置

### 客戶要做的事

| # | 動作 | 取代原本的關卡 |
| --- | --- | --- |
| 1 | GitHub：點「從範本建立」，再安裝 App 並只選這個 repo | 登入、建專案、填網址、貼 Token 共 4 關 |
| 2 | Supabase：貼 1 個 Access Token | 登入、建專案、填網址、貼 Token 共 4 關 |
| 3 | LINE Messaging：貼 Channel ID、Channel Secret | 原 3 關；長效 Token 那關拿掉 |
| 4 | LINE Login：貼 Channel ID、Channel Secret，並把狀態改成 Published | 原 3 關 |
| 5 | 按「開始建置」 | 核對、自動建置 2 關 |
| 6 | 到 LINE 後台開啟 Webhook、關閉自動回應 | 原 1 關（LINE 沒有 API，省不掉） |
| 7 | 加自己的 OA 好友，傳綁定碼 | 取代手動輸入 `runtimeOwnerId` |

27 關變成 7 個動作，其中要貼的值共 5 個。

### 系統做的事

1. 平台用 GitHub App 取得客戶 repo 的加密公鑰；瀏覽器用它加密 Supabase Token 與 LINE 的 4 個值；平台把密文寫進 repo 的 Actions Secrets。
2. 平台把固定範本寫進 repo，觸發 workflow。
3. 客戶 repo 的 Actions 執行：建立或選用 Supabase 專案、建資料表、部署 Webhook、設定 secrets、設定 LINE Webhook 網址、建立 LIFF、建立圖文選單、寫入初始設定資料、發布 Pages。
4. 平台讀 repo 裡的狀態檔顯示進度。
5. 完成後發一組 6 位數綁定碼（10 分鐘有效）。客戶在自己的 OA 傳這組碼，Webhook 把傳訊者記為擁有者。
6. 平台呼叫 GitHub API 移除這次的 App 安裝，建置頁顯示「Aprico 已移除對你 GitHub 的存取」。

LINE 的使用者 ID 每個 Provider 都不同，所以客戶在 Aprico 的 ID 不能直接當成他自己 OA 裡的擁有者 ID，必須用綁定碼。

### 固定範本的內容

| 元件 | 內容 |
| --- | --- |
| 設定資料 | 一份 JSON，格式沿用現有 `Draft`（`src/model.ts`），存在客戶的 Supabase |
| Webhook | 驗簽章 → 讀設定 → 選單回覆、卡片、秘書紀錄；擁有者的修改指令轉給平台 API |
| LIFF 頁 | 讀設定顯示卡片與表單 |
| 圖文選單 | 依設定的格數、配色、印花產生 |

**GitHub repo 的建立方式（已查證，不做 App 代建）**
- 社群討論指出，GitHub App 裝在**個人帳號**時，App 的安裝 token 不能幫使用者建 repo，必須用使用者本人的 OAuth token。就算用 OAuth token 建好，App 若只授權「選定的 repo」，新 repo 也不會自動加入授權。
- 所以流程固定為兩下：① 點「從範本建立」（`github.com/PTgamingLife/oaw-template/generate`）② 安裝 App 時只選這個 repo。
- 前提：`oaw-template` 要在 Settings 勾選「Template repository」。

**GitHub App 新增權限（已查證，GitHub 官方文件）**
- 新增 Actions、Secrets、Workflows 寫入權限後，每個已安裝的帳號都會收到 email，**核准前仍維持舊權限**；拒絕也保留舊權限。
- 建置中心在開始前先檢查權限，不足時顯示「到 GitHub 核准更新」的教學與連結（沿用現有的權限修復提示）。

## 5. 階段三：在自己的 OA 跟秘書對話修改

```
擁有者在自己的 OA 說：「第 3 格改成預約，按了回一張卡片」
  → 客戶的 Webhook 確認是擁有者 → 呼叫平台 API（附上那句話＋目前設定）
  → 平台 AI 回傳：修改後的設定＋白話摘要＋這次會扣幾點
  → 秘書回覆：「我會把第 3 格改成『預約』，按下後回一張卡片。這次扣 X 點，要套用嗎？」
  → 擁有者回「套用」→ Webhook 寫入自己的設定資料，必要時重建圖文選單
```

- 可以改的範圍（v1）：選單格數與每格內容、配色與印花、回覆文字與卡片、秘書的紀錄項目與回覆格式、失敗處理與轉人工文字。
- 不在 v1 範圍：新增 LIFF 頁面類型、接外部服務、自訂資料表。這些要改範本程式，另外處理。
- 平台回傳的設定一律經過現有的 `validateDraft` 檢查，Webhook 套用前再檢查一次；不合格就不套用、不扣點。
- 只有擁有者能進入修改；一般好友的訊息走正常服務。
- 平台 API 不保存客戶的設定與對話內容，只記錄用量。
- 沒按「套用」就不寫入。取消時是否扣點見第 6 節。

現有的「在 Aprico 官方 LINE 對話設計」（`chat-design.ts`）保留為建置前的試用與設計；建置後的修改都在客戶自己的 OA 進行。

## 6. 訂閱與額度

### 已決定（營運者 2026-11-11）

| 項目 | 決定 |
| --- | --- |
| 收費 | 改成**月訂閱 NT$370**，取代單筆購買與點數方案 |
| 成本目標 | 每位會員每月的 API 成本約為售價的 1/5，也就是約 **NT$74** |
| 顯示方式 | 使用者只看到**百分比**：「本月額度 100%，剩 63%」。不顯示點數、金額、token |
| 扣點時機 | **有對話就扣**，包含擁有者沒套用的修改提案、一般好友使用秘書 |
| 額度用完 | 發提醒，再給每人一次「價值 NT$20」的緩衝額度；同時鼓勵臨時加購 NT$30–50 |
| 已購買者 | 依過去購買金額，直接給一年額度 |

### 內部換算（使用者看不到）

- 每月額度 = 100%，對應 API 成本上限 NT$74。
- 每次對話扣的百分比 = 該次 API 成本 ÷ 74 × 100%。
- 加購 NT$X：增加 X ÷ 370 × 100% 的額度（NT$50 約 13.5%）。
- 費率（成本倍數、每月成本上限、匯率）放在費率表，調整時不用改程式。現有扣點公式寫死「成本 NT$1 扣 10 點」，要改成從費率表讀取。

### 實測計畫（定價前要做）

| 操作 | 量什麼 | 次數 |
| --- | --- | --- |
| 秘書一般回覆 | 每則的 token 用量與成本 | 20 |
| 秘書紀錄（行程、收支、待辦、生活） | 同上 | 各 10 |
| 健康秘書（量測紀錄、提醒、每日摘要） | 同上 | 各 10 |
| 修改設定（小改：一格文字） | 同上 | 10 |
| 修改設定（大改：整組選單） | 同上 | 10 |

輸出：每種操作平均扣幾 %、一個月 100% 大約能用幾次。實測會呼叫付費 API，執行前另外取得同意並先報預估費用。

### 防盜用

- 每把客戶 API 金鑰加上每分鐘、每日上限；超過就暫停並私訊擁有者。
- 擁有者可在自己的 OA 說「重設金鑰」，舊金鑰立即失效。
- 營運者的 OpenAI 帳號另設每月花費上限。

### 已確認的細節（2026-11-11）

| 項目 | 決定 |
| --- | --- |
| 緩衝額度 | 以售價計：價值 NT$20，**每月一次** |
| 顯示方式 | 主橫條：本月額度百分比。另一條橫條：緩衝額度與加購的剩餘，**用實際金額顯示**（例如「加值剩 NT$32」） |
| 已購買者 | 一年 = 連續 12 個月，每月給一份月訂閱額度。目前沒有只買 NT$1,680 點數方案的人 |
| 扣款順序 | 月額度 → 緩衝額度 → 加購 |

### 🟡 待確認

1. 訂閱的扣款方式：LINE Pay 自動扣款需要另外申請 ❓；不行的話改為每月手動續訂並提醒。

## 7. 第二套固定範本：個人健康 AI 秘書

> 狀態：方向已定，內容待確認。標 🟡 的項目要先決定才能做。

### 用途

協助長輩透過自己的 LINE OA 關注與記錄健康；照顧者（家人）透過同一個 OA 收到提醒與摘要。

### 功能（v1 草案）

| 功能 | 說明 |
| --- | --- |
| 量測紀錄 | 長輩用對話或 LIFF 表單記錄血壓、血糖、體重、服藥；AI 把一句話整理成欄位，確認後才存 |
| 提醒 | 量測、吃藥、回診提醒，依設定時間推播 |
| 對話關心 | 每日問候；長輩回覆後由 AI 整理成當日紀錄 |
| 照顧者通知 | 數值超出長輩或照顧者設定的範圍、或提醒後一段時間沒有回應，就通知照顧者 |
| 共用行事曆 | 回診與量測排程，照顧者可以一起看 |
| 每日／每週摘要 | 長輩本人與照顧者各收一份 |
| 看健 | 以 `mainwork/facialmonitor`（臉＋舌拍照分析）為主，放進 LIFF 選單 |
| 定時健康週報 | 每週彙整量測、看健結果與提醒完成率，推播給長輩與照顧者 |

### 照顧者怎麼連上

照顧者也是**同一個 OA 的好友**。長輩在 OA 產生一組邀請碼，照顧者加好友後傳邀請碼，長輩確認後才綁定。長輩可以隨時解除。

### 必須先處理的風險

1. **醫療定位**：只做紀錄、提醒與通知，不做診斷、不給用藥建議。所有異常通知固定附上「請諮詢醫師；緊急狀況請撥 119」。
2. **個資法**：健康數據屬於特種個資，蒐集前要取得長輩本人明確的書面同意（LINE 內勾選同意＋留存紀錄）。分享給照顧者也要另外同意。
3. **資料位置**：健康資料只存在客戶自己的 Supabase。送到平台 AI 處理時只送當次需要的內容，平台不保存。
4. **現有工具的安全問題**：`mainwork/facialmonitor`（看健）目前把臉部與舌頭照片上傳到**公開**的 Storage，任何拿到網址的人都看得到；點數也是由瀏覽器直接扣，可以被竄改。放進範本前必須改成私有儲存與後端扣點。

### 已確認的細節（2026-11-11）

| 項目 | 決定 |
| --- | --- |
| 健康工具 | 看健為主，附加定時健康週報 |
| 照顧者 | 加入**同一個 OA** 好友，用邀請碼綁定 |
| 共用行事曆 | 暫時做在 OA 內的頁面，不同步 Google 日曆 |
| 扣誰的額度 | 長輩自己的 |

## 9. 實作順序

每一步各開一個 PR，都不影響線上，直到營運者合併與部署。

1. 範本 repo：固定範本的 Webhook、LIFF、Actions workflow（在 `oaw-template`）。
2. 平台：GitHub App 寫入密文 Secrets 與觸發 workflow；綁定碼。
3. 前端：建置中心改成兩題＋7 個動作。動手前先提供畫面規格確認。
4. 平台 API：修改設定的端點；範本 Webhook 的擁有者修改流程。
5. 訂閱與額度：費率表、百分比顯示、緩衝額度與加購、防盜用上限；跑實測。
6. 健康秘書範本（決定第 7 節的 🟡 之後）。
7. 移除退場模組，更新文件與銷售政策草稿。

## 10. 平台私鑰的保護

GitHub App 私鑰外洩，攻擊者就能操作所有還裝著 App 的客戶 repo。對策：

| 對策 | 狀態 |
| --- | --- |
| 建置完成後自動移除 App 安裝，曝險只剩「建置中」的客戶 | 待實作 |
| 每次只發單一 repo、最小權限、一小時失效的 token | 已實作 |
| 私鑰只放 Supabase Edge Secrets，不進 GitHub、不寫 log | 已實作 |
| 定期換私鑰（先加新的再刪舊的，服務不中斷） | 營運流程，待訂週期 |
| GitHub、Supabase 管理帳號開兩步驟驗證 | 營運者確認 |
| App 安裝、移除、權限變更的通知，異常時提醒營運者 | 待實作 |

**LINE 金鑰維持由客戶自己貼（2026-11-11 決定）。** 不採用「客戶邀請營運者帳號當 LINE Developers Admin 代操作」：LINE 沒有 API 能自動解除角色，而且解除後營運者看過的 Channel Secret 仍然有效，要真正撤銷必須重新發行並更新客戶的 Supabase。

## 11. 已知限制

- LINE 的三件事沒有 API：建立 Login channel、改成 Published、開啟 Webhook。
- 平台可以寫入客戶 repo 的 workflow，理論上有能力讀到 Secrets。緩解：範本公開、固定版本、建置完成後提示移除 App 授權。
- 修改設定時，那一句話與目前的設定會送到平台與 AI 供應商處理；建置頁與銷售政策要寫明。
- 現有銷售政策草稿寫的是單筆購買與「5 次 AI 建置」，改成訂閱制後要重寫；已購買者依第 6 節補償。
